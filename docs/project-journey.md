## Stage 0 — From an empty repository to a governed assignment baseline

Completed and reviewed on 2026-10-10; committed as **51f27b2 — docs: establish project governance and assignment baseline**.

- **Starting state:** An empty Git repository on master, with no commits or tracked project files. The user then supplied the original Urumi assignment DOCX under docs/source/.
- **Problem:** We needed to preserve the actual assignment, prevent scope drift, and establish a process in which the user could understand and review each engineering change before application work began.
- **Concepts:** Source of truth versus interpreted requirements; mandatory scope versus optional stand-out work; traceability from requirements to demonstrations; documentation approval versus implementation evidence.
- **Decision:** Preserve the original DOCX and create a faithful Markdown reading copy. Establish AGENTS.md, ignore rules, README, requirement/demo matrices, and architecture, decision, security, and progress documents. Keep technical choices proposed until separately reviewed.
- **Alternatives:** Working only from the DOCX would make later sessions harder to navigate. Replacing its wording with best practices could change scope. Generating an application scaffold immediately would cross the agreed learning/review boundary.
- **Why this approach:** It made the assignment durable and reviewable while keeping its mandatory requirements, bonus items, demos, deliverables, and evaluation expectations distinct.
- **Repository/components affected:** Nine governance text files plus the preserved source DOCX. There were no application components. After approval, the branch was renamed from master to main and the ten files formed the first commit.
- **Validation performed:** The transcription matched all 169 nonempty paragraphs in order, 119 list entries, and 29 heading depths. Source checksum, 40 local links/anchors, Markdown formatting, ignore behavior, and the complete governance diff were checked. Tracking covered 44 requirement rows, 11 live demos, 6 video groups, 10 optional items, and 7 interpretation questions. The staged checkpoint contained only the reviewed governance/source files; the first commit left a clean working tree.
- **What we learned:** A written plan does not demonstrate a working requirement. Separate requirement and demo matrices reveal obligations that a happy-path demo alone would miss, including all five WooCommerce tools, hashed keys, and failure isolation.
- **How this enabled the next stage:** Stable requirement IDs and visible uncertainties gave Architecture v1 a concrete scope and review vocabulary before selecting implementation boundaries.

## Stage 1 — Architecture v1 review before implementation

Design and documentation reviewed and approved on 2026-10-10; committed as **db49836**. No MCP prototype, application, schema, or deployment has been created.

- **Starting state:** Approved governance on main at 51f27b2, with a proposed technology baseline and unresolved architecture/demo mechanics. No runnable system existed.
- **Problem:** We needed a small deployable design with explicit tool routing, user identity, credential ownership, failure behavior, and deployment boundaries before writing code.
- **Concepts:** REST versus MCP responsibilities; an MCP gateway as both client and server; configured state versus observed health; authoritative name mapping; sessions versus API keys; credential verifiers versus recoverable service secrets; logical reuse versus separate services; internal addressing versus caller isolation.
- **Decision:** Approve A1–A13: one modular Python/FastAPI backend; browser REST and external MCP entry points; official SDK/Streamable HTTP upstreams; simple slug-prefixed names with stored routing; separate health/configuration and stale metadata; sessions, roles, and hashed/revocable keys; workload-scoped Secrets; seven persistence entities; chat through the shared gateway path; one namespace and one Helm release; deterministic arithmetic/reference upstreams; explicit demo interpretations.
- **Alternatives:** Separate backend services, a browser MCP client, permanent connection strategy chosen before a prototype, always-suffixed tool names, direct upstream chat calls, external-service-dependent auxiliary servers, and Calico/custom NetworkPolicy prerequisites were considered. The review chose simpler initial boundaries and deferred details needing runtime evidence.
- **Why this approach:** Shared gateway logic keeps chat and external calls under the same authorization, timeout, routing, and audit behavior. Deterministic upstreams make the cross-server demo reproducible. Simple names and a stored mapping preserve understandable labels without making routing depend on parsing them.
- **Repository/components affected:** Architecture and decision records now describe the accepted contracts; progress and working rules reflect the boundary. This journey was added, and README, requirements, and threat-model wording were aligned. These are descriptions of future components, not implemented interfaces.
- **Validation performed:** A1–A13 were reviewed by the user. Documentation link/reference, formatting, source-preservation, scope, and status checks passed; evidence is recorded in [progress.md](progress.md#validation-and-review-record). Complete text diffs accompany this recording step's review. No SDK/client, authentication, Kubernetes, Helm, or live demo behavior has been tested.
- **What we learned:** Approval can fix a boundary while leaving mechanisms open. A disabled server is intentionally hidden; an unreachable enabled server retains stale metadata. ClusterIP does not prove isolation inside the cluster. Store timezone defines today, and the required rollback explanation does not automatically require executing an optional live rollback.
- **How this enables the next stage:** A later, separately authorized milestone can plan focused compatibility/prototype checks against these contracts, rather than scaffold the whole system. Package versions, connection lifecycle, Secret management, and client refresh behavior still need evidence.
- **Git reference:** db49836 — docs: define architecture v1 and project journey; based on 51f27b2.

## Stage 2 — Environment preflight and local cluster selection

Preflight reviewed and k3d selected on 2026-10-11. This completes the preflight/decision checkpoint only; the Kubernetes foundation is not installed or running.

- **Starting state:** Architecture v1 committed as db49836 on main, with its commit-reference update still unstaged in this journey. That update is included in this documentation checkpoint.
- **Problem and concepts:** Establish readiness before installation and choose a practical Windows host-to-Ingress path. A container runtime, cluster tool, and Kubernetes Ingress have distinct responsibilities; total RAM is not the same as available capacity.
- **Preflight evidence:** Git 2.44.0.windows.1, Python 3.13.6 through both python/py, Node 22.18.0, and npm 11.6.1 were already available. Windows 11 had WSL 2.5.9 with WSL2 as the default, its supporting Windows features enabled, and no installed distributions. Docker Desktop/engine, kubectl, and Helm were not detected; the supplemental k3d check also found no installation. Existing Docker context metadata did not establish a running engine.
- **Resource findings:** About 24 logical CPUs and 110 GiB free on the repository drive supported initial planning. Of roughly 15.7 GiB total RAM, only 2.6–2.8 GiB was available during preflight. Memory headroom must be rechecked before starting a cluster; a workable full-system resource budget has not been demonstrated.
- **Decision, alternatives, and rationale:** DEC-017 selects k3d with Docker Desktop as the intended runtime, replacing the proposed Minikube Docker driver. Windows host-access limitations would complicate stable Ingress with that Minikube setup; k3d provides explicit Docker host port mappings. Running k3s locally also aligns with the proposed k3s VPS. Kind and Minikube remain assignment-permitted alternatives. This is an implementation choice, not a new requirement.
- **Repository/components affected:** Architecture, decisions, progress, this journey, and the stale local-baseline references in README and requirements. The existing Architecture v1 checkpoint update is preserved. No application or deployment components were created.
- **Validation and learning:** Read-only environment inspection and official tool documentation informed the change; no installation, cluster, or runtime test occurred. Preflight can revise a proposed tool choice before it becomes costly to change. Documentation checks for this checkpoint are recorded in [progress.md](progress.md#validation-and-review-record); runtime requirement and demo statuses remain unchanged.
- **How this enables the next stage:** A later reviewed step can select versions, plan installation and resource allocation, and validate Docker plus stable local Ingress before application deployment. Neither stable access nor local-to-VPS parity is proven yet.
- **Git reference:** 1f2aec9 — docs: select k3d after environment preflight; based on db49836.

## Stage 2.2A — Docker Desktop setup and runtime validation

Initial installation attempt blocked on 2026-10-11; the user then installed and started Docker Desktop manually. Runtime validation and documentation were reviewed and approved; committed as **84395d5** on 2026-10-11.

- **Starting state and problem:** Clean main at 1f2aec9. Establish the Linux-container runtime that k3d will later use, before installing cluster tools or creating project workloads.
- **Plan and rationale:** WinGet 1.29.380 identified Docker.DockerDesktop 4.94.0 and its Docker-hosted installer. The initial plan selected the official per-user path with WSL2/Linux containers and Docker Desktop Kubernetes disabled, covering the runtime need without all-users elevation. First-run agreement acceptance was left to the user.
- **Initial blocker:** Read-only checks reconfirmed Docker absent and WSL 2.5.9 with its Windows features enabled. The installation command was rejected before execution with "blocked by policy" and no further reason. No installer download, checksum/signature verification, or installation ran through Codex. Codex did not attempt an alternate execution route; the user subsequently installed and initialized Desktop manually, then authorized validation.
- **Validation and outcome:** Desktop 4.94.0 and CLI/Engine 29.8.2 responded successfully through the unchanged desktop-linux context. The server reports linux/amd64 and a WSL2 kernel; docker-desktop is Running under WSL version 2. Desktop Kubernetes status is disabled/stopped. The installer had updated the persistent user PATH; Codex's older process needed only a process-local PATH refresh. The detailed check results are in progress.
- **Learning validation:** One `docker run --rm hello-world` succeeded with exit 0. The Windows CLI sent Docker API requests through Desktop's local named pipe to the Linux engine. Because the image was absent locally, Docker pulled it from Docker Hub and cached its image data; inspection shows one immutable filesystem layer and the /hello command. Docker created an isolated container with a writable layer, ran /hello, and relayed its greeting through the engine and CLI to the terminal. On process exit, `--rm` removed the container and its writable layer. Both the hello-world container listing and total container count were zero afterward; the image remains cached for reuse.
- **Learning and limits:** CLI availability, engine reachability, and Linux/WSL2 operation now have runtime evidence. An image is a reusable template; a container is a created runtime instance. Automatic container removal does not delete the cached image. This establishes the Docker prerequisite for k3d, not a Kubernetes cluster, stable Ingress, or full-system resource capacity.
- **Repository and next step:** Only progress and this existing journey entry change; assignment, architecture, and requirement/demo statuses remain unchanged. No project containers, Dockerfiles, application directories, or Kubernetes resources were created, and no k3d/kubectl/Helm installation was performed. Stop for review before the next tooling step.
- **Git reference:** 84395d5 — docs: record validated Docker runtime; based on 1f2aec9.

## Stage 2.2B — Kubernetes CLI toolchain setup

Tool installation, client validation, and documentation were reviewed and approved; committed as **248f13c** on 2026-10-11. No cluster was created in that step.

- **Starting state and problem:** Clean main at 84395d5 with a verified Docker Desktop WSL2/Linux engine. Establish the CLIs needed for a later k3d/K3s environment without starting its control plane or deploying workloads.
- **Concepts and decision:** K3s supplies Kubernetes; k3d manages K3s nodes in Docker; kubectl operates against the Kubernetes API; Helm packages and manages application releases. Reuse Docker Desktop's existing kubectl v1.36.1 and install k3d v5.9.0 plus Helm v4.3.0 through WinGet in user scope.
- **Alternatives and rationale:** The official Kubernetes.kubectl package was available, but a duplicate install would introduce another binary/PATH choice without a present need. Verified k3d.k3d and Helm.Helm manifests download directly from the upstream k3d GitHub release and get.helm.sh. WinGet managed aliases/PATH and verified download hashes; no unofficial binary host, policy workaround, or elevation was needed.
- **Validation performed:** All three version commands exited 0. k3d reports default K3s v1.35.5-k3s1; this is metadata, not a running server or an agreed cluster version. kubectl contexts and k3d clusters were empty, no kubeconfig was created, Desktop Kubernetes remained disabled, and Docker had zero containers. The unset-current-context result was expected. No API context was changed or Kubernetes resource created.
- **Learning:** Installing tools does not create a cluster. Helm manages chart releases but kubectl is still needed to inspect resources, logs, and events. Existing shells may need a PATH refresh after installation. Version-command success proves executable availability; actual cluster compatibility, Ingress access, and resource capacity still need later validation.
- **Repository and next step:** Only progress and this journey change, including recording the preceding approved commit. Assignment requirements, demo statuses, and architecture decisions remain unchanged. Stop for review before choosing cluster versions, sizing, and host port mappings or creating any cluster/chart/application files.

## Stage 2.3 — First local Kubernetes cluster

Infrastructure creation and validation completed on 2026-10-11; documentation awaits review and remains uncommitted. No application workload was deployed.

- **Starting state and problem:** Clean main at 248f13c, with a verified Docker Linux engine and installed CLIs. Move from tool availability to a real, inspectable Kubernetes control plane while preserving the infrastructure-only boundary.
- **Prechecks and resource judgment:** No k3d clusters or kubectl contexts existed; Desktop Kubernetes was disabled. Ports 6550/8080/8443 had no bindings or Windows exclusions and passed temporary bind checks. Windows had about 2.79 GiB available of 15.73 GiB RAM; Docker's WSL environment separately reported about 6.93 GiB available within its virtual memory capacity. These are not additive. The single empty server was judged feasible against K3s's 2 GB baseline; a full application resource budget was not established.
- **Decision and rationale:** Follow the user's one-server/zero-agent plan with k3d v5.9.0's default K3s image. Bind the API to loopback port 6550 and map host 8080/8443 through k3d's load balancer to 80/443. Keep Traefik, CoreDNS, metrics-server, local-path storage, and default networking; add no separate CNI/NetworkPolicy tooling. Extra nodes or replacing bundled components would add work without helping this learning milestone. The exact supported command is recorded in progress.
- **Observed configuration:** urumi-local runs Kubernetes/K3s v1.35.5+k3s1 with containerd 2.2.3-k3s1. Its sole node is k3d-urumi-local-server-0; the selected context is k3d-urumi-local. Docker also shows the serverlb proxy and tools helper, neither of which is a Kubernetes node. k3d wrote personal kubeconfig outside the repository and created its Docker network/image volume. Only default, kube-system, kube-public, and kube-node-lease namespaces exist.
- **Validation and recovery:** Creation returned successfully after about 54 seconds, then independent checks confirmed node Ready, API readiness, all four system Deployments available, the Traefik ServiceLB ready, and both bootstrap Jobs complete. Initial Flannel initialization warnings and a metrics-server image-pull EOF recovered automatically; one Traefik installer restart ended in completion. Metrics retrieval works. The default local-path StorageClass uses Delete and WaitForFirstConsumer; no PVC was tested. HTTP port 8080 returns Traefik's expected 404 without an application route, while HTTPS/TLS remains untested. Desktop Kubernetes stayed disabled.
- **Learning:** Windows hosts Docker Desktop's WSL2 Linux engine; Docker runs the k3d infrastructure containers; K3s inside the server container registers a Kubernetes node and uses its own containerd runtime for system Pods. The K3s server combines control-plane/datastore responsibilities with kubelet/runtime duties, so the single untainted node can also run workloads. docker ps shows the outer containers; kubectl queries Kubernetes objects through the API server. Kubeconfig supplies endpoint/trust/authentication information, and a context selects a cluster, user, and optional namespace. The API server authenticates/authorizes requests and provides the interface through which controllers and clients read/update cluster state.
- **Limits and next step:** Post-startup Windows available RAM was about 1.28 GiB; node metrics showed roughly 727 MiB, which excludes much host overhead and is not an application budget. Reassess headroom before expanding. Ready infrastructure does not complete the assignment's local application, stable URL, persistence, or Helm requirements. No project resources, nginx learning workload, application files/directories, charts, or Dockerfiles were created; only progress and this journey change. Stop for review before further learning workloads or implementation.
- **Git reference:** Uncommitted documentation following 248f13c; no commit authorized for this step.
