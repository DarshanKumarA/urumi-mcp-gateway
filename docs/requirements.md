# Requirements and demonstration traceability

The [original DOCX](source/urumi-mcp-gateway-assignment.docx) is authoritative; [assignment.md](assignment.md) is its faithful reading copy. This document is a derived tracking view, not a replacement specification. Source labels below identify the assignment's actual headings: **Mandatory** means “Requirements (mandatory)”; **Stories** means “User stories”; **Done** means “Definition of done (must be testable)”; **Submission** means “Demo video and submission (mandatory)”.

Requirement IDs remain stable when plans change. Architecture v1 choices A1–A13 are accepted in [decisions.md](decisions.md) as DEC-004 through DEC-016; DEC-017 selects k3d after environment preflight. Store Architecture v1 is now accepted as DEC-018–DEC-021; its current store-specific contracts supersede the matrix's earlier planning placeholders (including checkout method and packaging) in [architecture.md](architecture.md#accepted-store-architecture-v1). Stage 3.3 adds store bootstrap/readiness implementation and available static checks; PHP syntax and runtime evidence remain pending. No store demo has run, and neither design approval nor the passing initial RAM gate proves a requirement works. Other unresolved details remain proposed. A verification plan is not evidence of passing it. “Not started” means no implementation/evidence for the complete requirement; “Draft only” means incomplete documentation exists, not that the requirement is satisfied. Future status changes must link to the relevant change and test/demo evidence. No requirement is currently marked implemented or verified.

## Evaluation expectations and interpretation questions

The assignment gives two weeks but no start or submission date; no calendar deadline is inferred here. It values a working core over unfinished bonus work, encourages AI use while requiring personal understanding and defense of decisions, and explicitly grades the chat tool loop rather than model-answer quality. Round 2 includes an interview/live walkthrough; Round 3 is with founders. No scoring weights are supplied.

Interpretations retain IDs OPEN-01 through OPEN-07 in [architecture.md](architecture.md#unresolved-assignment-interpretations). A13 records reviewed approaches for upgrade/rollback scope, invitation mechanics, disabled catalogs, revoked-key attribution, failure observation, client validation, and store timezone. SDK/client refresh behavior, precise security/tool contracts, and actual demo procedures still require implementation-time validation. No assignment source wording or mandatory/optional classification is changed by these plans.
